# Limitations, vulnerabilities and honest assessment

1. **No real data was run.** Everything quantitative comes from synthetic, LendingClub-shaped data. The real-data loader is untested.
2. **Synthetic circularity.** Loans are generated from a logistic model, then fitted with a logistic model. A good fit is expected and proves little.
3. **The hybrid link is artificial.** LendingClub borrowers never sat on a bank balance sheet. GL and loans are tied only through `--anchor-ead`. Even so, modelled EL (13.6% of EAD) is ~3× the booked allowance (4.6%): the reconciliation view makes the mismatch visible rather than hiding it.
4. **PD horizon.** PD is a resolved-loan default probability, not 12-month. No lifetime term structure, no IFRS 9 staging, no CECL, no macro overlay. EL is a risk estimate, not a compliant provision.
5. **LGD is a single portfolio proxy** (recoveries ÷ original amount); no segmentation, no discounting of recoveries.
6. **Selection bias and censoring.** Only accepted applicants; no reject inference. Out-of-time test covers a short window.
7. **Balance-sheet check.** `v_balance_sheet_check` assumes P&L activity exists in every month; the cumulative-earnings CTE does not use the calendar spine, so a month with zero P&L postings would understate equity. Not triggered by the sample data; fix before using on a sparse ledger. No year-end closing entries are modelled (equity = booked + cumulative P&L).
8. **IV filter cost.** The ≥ 0.02 rule discarded `revol_util` (IV 0.019) and `term` (0.016), which are real drivers in the generator. Only 4 features survived. IV depends on binning, so thresholds are heuristics, not tests. The > 0.5 rule did correctly flag `int_rate`/`grade` as leakage.
9. **Modest discrimination.** Test Gini 0.27 / KS 0.20 / AUC 0.64 on synthetic data. At the KS-optimal cutoff accuracy is ~62% with bad-class precision ~23% — fine for ranking and banding, poor as a hard accept/reject rule. The cutoff is not cost-optimal; a business cutoff needs cost of default vs. lost margin.
10. **Constraint vs diagnostics.** Scorecard uses sign-constrained LR (slopes ≤ 0, tiny L2). The statsmodels p-values/VIF are from an *unconstrained* refit of the same features and are diagnostic only.
11. **Variance/GL simplifications.** Fiscal year = calendar year; one budget version; no accruals, FX, intercompany, tax, or reversals. Default ledger is only 790 lines; `--split` inflates to 312k.
12. **Performance claims are small.** With 312,002 ledger lines: materialised-view refresh ≈ 0.4 s, full 18-check audit ≈ 0.6 s, variance/P&L/BS views in milliseconds (single local PostgreSQL 16, no tuning). That shows the design is sound at this size; it is **not** evidence for tens of millions of lines, where partitioning by posting_period and incremental refresh would be needed. Python on 200k loans runs in seconds.
13. **DAX, Qlik, Power Automate are unexecuted.** Written to the tested SQL schema; must be validated in the real tools. Power Automate connectivity (Premium HTTP, gateway behaviour, NPrinting API paths) must be confirmed against your licensing and versions.
14. **Governance gaps.** No model risk management documentation (SR 11-7-style), no fair-lending analysis (features like home ownership can proxy protected classes), no access control, no secrets management, no CI. Board numbers should not go out without sign-off.
15. **Staleness hazard.** Sample reporting period is 2021-12 while the EL snapshot is 2019-03; `v_board_kpis.el_months_stale = 33` and the Power Automate gate refuses to send. Intended behaviour, but it shows how easily a stale risk number could reach a board.
